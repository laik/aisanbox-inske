# POC-OP 追加轮 2：一个新租户 T-50933 的接入方式（角色不随系统增长）

时间：2026-11-23T10:23:08Z ~ 10:26:20Z（`FORCE_KC=1 bash 90-oidc-ns-workspace.sh`，原始日志在第 3 节）
环境同上一轮（`k8s-221`、chart 0.1.7、CLI 0.1.9、Keycloak 26 在 ns `identity`）。

## 1. 要回答的问题

OpenShell 想限定 `T-50933-ADMIN` / `T-50933-USER` 这两个 OIDC 组，但不想像 OpenShell 内置角色那样
"每接一个系统就得加一批角色"；以及对应的 workspace 怎么办。

## 2. 结论

| 编号 | 判定 | 内容 |
|---|---|---|
| O-11 | ✅ | token 里带 `T-50933-USER`（外加 `os-user`）**不等于**能进 t-50933：`not a member of workspace 't-50933'; ask a platform admin to run: openshell workspace member add --workspace 't-50933' --subject 'u50933' --role user`。租户组不参与 OpenShell 判定 |
| — | ✅ | 平台 Controller 只做一件事：`T-50933-USER → workspace t-50933 member user`、`T-50933-ADMIN → 同 workspace member admin`。做完 u50933 立刻能建沙箱 |
| O-12 | ✅ | 同步后 u50933 能在 `t-50933` 建沙箱；对 `tenant-a-runtime` 仍被拒 → 边界仍然是"同名 workspace 的成员" |
| O-13 | ✅ | `a50933`（T-50933-ADMIN → Workspace Admin）能在 `t-50933` 加成员、列成员；对 `tenant-a-runtime` 被拒。**租户管理员 ≠ `os-admin`**：`os-admin` 是全平台（可跳所有租户，见上一轮 O-05） |
| 落点 | ✅ | 新租户的沙箱 `tc-1` 落在新 ns `t-50933`；建 ns + 打标 + 装 workspace chart 之后 **Gateway 不用重启**（标签 watcher 自动发现），`workspace create --name t-50933` 即可 |
| claim | ✅ | 两个新身份的 claim 只有 `['T-50933-USER','os-user']` / `['T-50933-ADMIN','os-user']`：**新接一个租户，OpenShell 的角色一个都没加**，Gateway 的 OIDC 配置一个字节都没改 |

对应关系就一行：**租户编号 → ns 名 = workspace 名**（`T-50933` → `t-50933`，DNS-1123、≤19 字符；
`T-50933-USER` 这种大写带后缀的名字只能当 IdP 组名，不能当 workspace/ns 名）。

## 3. 本轮新踩的坑（都在 Keycloak 侧，症状都会伪装成 OpenShell 的问题）

1. **ConfigMap 用 delete+create 更新，运行中的 Pod 就不再同步这个挂载** → Keycloak import 的还是上一版 `realm.json`，
   表现是"realm 改了不生效 / 新用户 user_not_found"。改成 `create --dry-run=client -o yaml | kubectl apply -f -` 原地更新；
   脚本里再断言 Pod 里挂的文件哈希 == 本地文件哈希（不匹配就直接失败），另加 `FORCE_KC=1` 强制重导入。
2. realm JSON 里 `"defaultRoles": ["os-user"]` **没有效果**（实测：import 停在 roles 中段，后面的角色和用户的 roleMappings 都没进来）。
   要"人人都带 os-user"，就在控制台配默认角色/默认组，或者像 POC 这样每人显式赋一次。
3. realm JSON 里组的 `subGroups` **不会被创建**（只建了顶层组），于是"把租户组挂在 os-user 下靠继承拿到 os-user"这条路在 `--import-realm` 里不成立。
4. 新建用户缺 `email`/`requiredActions` 时，密码授权报 `invalid_grant: Account is not fully set up`，
   看起来像密码错，其实是账号被判定"未设置完整"。补 `"requiredActions": []` + email 后正常。
