## 1. 结论

| 编号 | 判定 | 内容 |
|---|---|---|
| R-01 | ✅ | `roles_claim` **支持点分路径**，chart values.yaml 的注释就写了 Keycloak 用 `realm_access.roles`。实测把 `rolesClaim` 从 `groups` 换成 `realm_access.roles`（Keycloak 默认就有的角色数组），带 `os-admin` 的人照样能 `workspace list`，带 `os-user` 且是成员的人照样能建沙箱 → **不需要在 IdP 里造自定义 claim** |
| R-02 | ✅ | 角色值必须**字面出现在那个 claim 里**。新加的用户 `p50933`（`realmRoles=[]`，claim 里角色数组为空）→ 所有操作被拒：`role 'os-user' required`。OpenShell 不会凭空造角色，也不会去 IdP 注册任何东西 |
| R-03 | ⚠️ | `adminRole`/`userRole` **都留空 ≠ 没有角色门**。chart 注释写的是 "authentication-only mode"，0.1.7 实测是：所有调用要求 **`role 'openshell-user' required'`** —— 即留空会回退到内置默认角色名 `openshell-user`。想"少配一个名字"可以用这个默认名，但 token 里还是得出现它 |
| R-04 | ✅ | 每租户的 `T-<id>-USER` / `T-<id>-ADMIN` **不能**用作 `userRole`/`adminRole`：这两个配置项各只接受一个字符串，没有列表、没有前缀/通配。租户内的管理员只能靠 workspace 成员角色 `admin`（第 8 节 O-13） |

## 2. 所以"在 IdP 定义还是 OpenShell 定义"

- **字符串在 OpenShell 的配置里定义**（`adminRole` / `userRole`，随你起名），这是唯一"定义角色"的地方。
- **token 里的值由 IdP 出**，必须与那两条字符串之一相同。所以 IdP 侧至少需要**一个全平台共用值**（不是每个系统一个），做法三选一：
  1. 目录里加一个组/角色（如 `openshell-user`；平台运维再加一个 `openshell-admin`）——总共两个，永不随租户增长；
  2. 不动目录，只在 client / scope 上加 mapper 注入（Keycloak Hardcoded claim / 组→自定义 claim；ADFS issuance transform rules；Dex static client）；
  3. 什么都不加：让 `adminRole`/`userRole` 留空，接受内置默认名 `openshell-user`（R-03），但 token 里仍要出现它。
- 无论哪种：`T-<id>-*` 组都不进 OpenShell，只进平台 Controller 的成员同步。
