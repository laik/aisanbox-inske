每一层挡的东西不同，不重复造轮子：能力型越权交给容器安全上下文，行为允许交给 OpenShell，独立真相与细粒度拦截交给 Tetragon。

层挡什么实测证据
Capsule租户边界：配额、ns 数量、存储类、默认网络护栏forbidden: exceeded quota: capsule-globex-0；删除后 status.used 正确回落
安全上下文能力型越权（mount / init_module / root）裸 mount() → errno 1 EPERM，seccomp 在 syscall 到达内核前挡住
agent-sandbox有状态单例：身份、持久卷、生命周期、预热claim 到 Ready 0.25s；PVC workspace-* 随沙箱创建
OpenShellagent 被允许做什么，以及为什么允许策略热更新 version 1→2, loaded，无需重启
Tetragon实际做了什么 + 按 binary×地址细粒度拦截agent:egress-external daddr=1.1.1.1:53；强制时 PermissionError after 0.11s
这不是拼装

OpenShell 的 Kubernetes compute driver 本身就构建在 agent-sandbox 之上：官方安装步骤要求先装 agent-sandbox CRD，网关创建 Sandbox CR，由该控制器落地 Pod。所以"这 3 个项目搭配"是它的官方路径，不是我们的组合发明。

02 · 接缝唯一需要接线的一处

模式namespace 归谁适用
shared全部落一个 ns单团队，隔离最弱
managedOpenShell 自建 ns没有既有租户体系时
operator平台预建，按 label selector 发现与 Capsule 对齐
# capsule/tenants.yaml — 租户侧：给该租户所有 ns 注入被发现的标签
apiVersion: capsule.clastix.io/v1beta2
kind: Tenant
metadata: {name: acme}
spec:
  owners: [{kind: Group, name: tenant-acme}]
  namespaceOptions:
    additionalMetadata:
      labels: {openshell.ai/workspace: "true", aisanbox.io/tenant: acme}
  resourceQuotas:
    items: [{hard: {limits.cpu: "4", limits.memory: 4Gi, count/pods: "40",
                    persistentvolumeclaims: "10", requests.storage: 20Gi}}]
  limitRanges:
    items:
      - limits: [{type: Container, default: {cpu: 500m, memory: 512Mi},
                  defaultRequest: {cpu: 100m, memory: 128Mi},
                  max: {cpu: "2", memory: 2Gi}, min: {cpu: 10m, memory: 16Mi}}]
# openshell/values-plane-a.yaml — 控制面：按该标签发现命名空间
server:
  sandboxNamespace: ""        # 必须留空(=release ns)；它同时是网关 Secret 的复制源
  drivers:
    kubernetes:
      workspaceMode: operator
      operatorNamespaceLabel: "openshell.ai/workspace=true"
workspaceResources:
  enabled: false              # 命名空间级前置交给每个租户的 openshell-workspace chart

网关日志确认接管：operator namespace allowlist replaced from full relist total=2。

03 · 沙箱形态一个沙箱实际长什么样

namespace acme   labels: capsule.clastix.io/tenant=acme · openshell.ai/workspace=true
├─ Sandbox CR    agents.x-k8s.io/v1beta1            ← OpenShell 建，agent-sandbox 落地
├─ pod poc-acme-1
│    labels: projectcapsule.dev/tenant=acme · openshell.ai/boundary-role=workload
│    └─ container agent   uid 10001 · drop ALL caps · 无 SA token · /sandbox 持久卷
├─ pod os-supervisor-…   openshell.ai/boundary-role=supervisor
└─ 三层 NetworkPolicy 叠加: capsule-acme-0 / openshell-sandbox-workloads / …-ssh
最值钱的性质

同一个 Pod 上同时带 Capsule 与 OpenShell 的租户标签。因此配额、网络边界、执行策略、内核审计四层能用同一个键 projectcapsule.dev/tenant 聚合与选择。Tetragon 的策略因此可以写成"该租户的所有沙箱"，而不是某个 Pod 或容器 ID。

04 · 使用样例开通一个租户，然后用它

开通：5 步，没有手工逐项配置

  1. Tenant（含上面那根接线标签）
  2. TenantOwner —— 不注册的话 owner 连 create ns 的权限都没有（默认 owner 只拿 admin + capsule-namespace-deleter）
  3. 由 owner 自己建 ns：kubectl create ns acme --as=alice --as-group=tenant-acme（Capsule webhook 注入标签/配额/LimitRange/默认 NP）
  4. 在该 ns 装 openshell-workspace chart —— operator 模式下这是网关在该 ns 内唯一的 Secret 权限来源
  5. 下发该租户的 Tetragon 策略（手工按租户替换标签，或用 GlobalTenantResource 自动下发）

租户侧日常

openshell workspace create --name acme
openshell --workspace acme sandbox create --name try1 \
  --cpu 200m --memory 256Mi -- python3 -u agent.py
openshell --workspace acme logs try1 --since 10m
openshell --workspace acme policy get try1        # 生效策略 + hash + version
openshell --workspace acme policy update try1 \
  --add-endpoint "api.github.com:443:read-only:rest:enforce" \
  --binary /usr/local/bin/python3 --wait          # 实测热更新成功 v1→v2

低延迟：按租户的预热池

池放在租户命名空间里，容量受该租户配额约束。同一集群、同节点实测：

路径到 Ready说明
认领预热池 SandboxClaim0.25 s已验证
冷启动，镜像已在节点0.92 s已验证
冷启动，需拉 20 MB 镜像15.98 s真实场景的多数情况
池会吃租户配额

实测：模板不写 resources 时 Capsule LimitRange 的 default 会被补上，实际占用 = replicas × default；池撑爆配额时 agent-sandbox 控制器报 exceeded quota: capsule-acme-0。行为正确（租户边界生效），但池容量必须进租户容量规划，模板必须显式声明 resources。

两个 kind 集群共享同一 Docker 网络，所以平台集群直接抓租户集群的 NodePort 即可；生产上是同一拓扑（federate / 远程写同理）。三处 target 全部 up：

kind: GlobalTenantResource
metadata: {name: aisanbox-agent-audit}
spec:
  tenantSelector: {matchLabels: {app.kubernetes.io/part-of: aisanbox-poc}}
  resyncPeriod: 60s
  resources:
    - namespaceSelector: {matchLabels: {capsule.clastix.io/tenant: acme}}
      rawItems:
        - apiVersion: cilium.io/v1alpha1
          kind: TracingPolicyNamespaced
          metadata: {name: tenant-agent-audit}
          spec: {kprobes: […]}

一个实际收益：快速失败 vs 挂起

拦同一个目的地agent 侧表现耗时
NetworkPolicy连接超时，会撑爆 agent 的超时/重试逻辑~6.0 s
Tetragon security_socket_connect + OverridePermissionError，agent 可立刻改道或报错0.11 s

并且它比 NetworkPolicy 更细：按"哪个 binary 连哪个地址"决定（实测只对 python3 生效）。

07 · 规则写策略前必须知道的 8 条

全部是这次实测踩出来的，其中 3 条我自己在写策略时踩到。tetragon.io 文档没有一处写全。

R1
一个 TracingPolicy 只能有一个 section

kprobes 与 lsmhooks 混写 → 整条策略不加载，报 tracing policies with multiple sections … are not supported。报错不指向具体行，很容易误判成别的错。把观测与强制拆成两个文件。

R2
kprobe 与 LSM 看到的"路径"不是同一个东西

sys_execve 的 args[0] = 调用者请求的路径（/bin/sh）；bprm_check_security 的 matchArgs args[0] = 解析后的真实文件（/bin/busybox）。同一个语义，两个视图。

caller=python3 --exec--> args[0]="/bin/sh"        # kprobe sys_execve
bprm   args[0]="/bin/busybox"                      # lsm bprm(已解析)
R3
在 bprm_check_security 上匹配执行目标要用 matchArgs，不是 matchBinaries

后者匹配的是调用者（那时二进制还没换），实测永不命中。官方样例 examples/tracingpolicy/lsm_bprm_check.yaml 就是这个写法。相反，在 security_socket_connect 上 matchBinaries 是正确且有效的（socket 由调用者建立）。

R4
BusyBox/Alpine 形态下按 /bin/sleep、/bin/sh 写 exec 强制永不命中

实测 /bin/sh、/bin/mount、/bin/echo、/bin/sleep 全部 → /bin/busybox，os.system() 照样通过。真实独立文件（pip、npm、bash）则能被精确拒掉。

/bin/sh    -> /bin/busybox     /usr/local/bin/pip -> 自身(可精确拦)
/bin/mount -> /bin/busybox     /bin/bash          -> 自身(可精确拦)

平台规范二选一：agent 运行时用 Debian/Ubuntu 基座并按 digest 固定；或按 busybox 形态写策略。

R5
socket 参数的操作符不能混用，错了不报错

type: sockaddr 只支持 SAddr / SPort / Family。对它用 DAddr：加载不报错，但永不匹配（我在这条上连着误判两次）。按目的地址筛连接要用 type: sock + tcp_connect。

R6
监听端口要用 security_socket_listen + type: socket

常见写法 inet_listen + sock 会解析出乱值（family:"27840", saddr:"invalid IP"）。改成前者后实测拿到真值 saddr=0.0.0.0 sport=31339。

R7
能力型越权不该靠策略，而且 Tetragon 也看不见

裸 mount() / init_module() 实测得到 errno 1 EPERM：seccomp + drop ALL caps 在 syscall 到达内核前就挡住了，因此 kprobe 完全没有事件。这是分层正确，不是漏采 —— 策略只该补"挡不住但可疑"的行为。

R8
glibc 的 rename() 走 sys_renameat

写 sys_rename（index 0/1）不会触发。正确是 sys_renameat(dirfd, old, newdirfd, new) → index 1 与 3。改完实测命中 /tmp/a → /tmp/b。

R9
版本获取陷阱（非 Tetragon，但会浪费半天）

文档 docs.nvidia.com/openshell/latest 讲 v0.1.6，而 GHCR tag 列表首页最高只有 0.0.42 —— registry 分页所致，真实最新稳定是 0.1.4。取 tag 必须分页拉全再按语义版本排序。

08 · 上线前7 项未验证或需处理

项状态细节与建议
沙箱 DNS 走 supervisor 边界未达成沙箱 resolv.conf 指向 127.0.0.53；到 cluster DNS:53 通，到 supervisor:53/:8080 超时。L7 策略热更新成功但请求没到边界，拿不到官方教程里 403 from proxy after CONNECT。先在自己的环境验这段，它决定"用 L7 策略放行出网"这条路径是否可用。
Capsule runtimeClasses 白名单未拦住设 allowed:[gvisor] 后用 tenant owner 建 runtimeClassName: kata-containers 被接受，到 kubelet 才失败。要按租户限制 gVisor/Kata，需自补一层 CEL ValidatingPolicy。
两条 sandbox 路径未打通缺口预热池认领出的沙箱不带 OpenShell supervisor / policy（无网络边界、无凭据注入）。要"低延迟 + 有策略"，需要 OpenShell 支持从池认领；目前 allow_driver_config 不提供该语义。
hypervisor 级隔离未做kind / Docker Desktop 无现成 gVisor 节点镜像。当前强度来自 supervisor + NP + 非 root + seccomp。跑不可信 LLM 代码仍需 gVisor/Kata。
OpenShell 多集群单集群K8s driver 用 in-cluster client，无 kubeconfig 选项 → 多集群只能每集群一套 gateway（联邦），或按租户分片。
HA需改默认 StatefulSet + 单副本 + SQLite 只够 POC。生产要 workload.kind=deployment + 外部 PostgreSQL，且 PostgreSQL 自身另做 HA。
Capsule 字段生命周期 / 所有权冲突注意resourceQuotas·limitRanges·networkPolicies·additionalMetadata 已标 deprecated（apply 时给迁移警告），方向是 rules + *TenantResource。GlobalTenantResource 对已由 Helm 管理的同名资源（如 openshell-sandbox SA）会 applying of 1 resources failed —— SA 要么交给 GTR，要么交给 per-ns Helm，二选一。
