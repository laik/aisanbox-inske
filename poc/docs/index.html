01

四层，各管一段

每一层只解决一个问题，组合起来才是"能放心跑 AI 代码"的环境。没有重复造轮子，每层都附了实测证据。

01

Capsule 租户合同0.15.2

决定谁住哪里：命名空间归谁、能用多少 CPU 内存、最多建几个 ns。像物业——分房、抄表、定水电上限。

{超配额直接被拒
exceeded quota: capsule-globex-0}
02

agent-sandbox 沙箱本体v1.0.9

提供那间房：稳定身份、可长期存东西的工作盘、休眠、预热池。像房间——有门牌、有储物柜，还能提前备好空房。

认领预热池 → 0.25 s 就绪
03

OpenShell 行为边界0.1.4

决定它能碰什么：哪些文件、哪些出网地址、哪个凭据，以及为什么放行或拒绝。像门禁——谁能进哪扇门，谁批的条子。

策略热更新 v1→v2，无需重启沙箱
04

Tetragon 真相与拦截1.8.0

记录真实发生的事：agent 在内核里到底碰了什么、想连哪里，并能在当场拒绝。像走廊摄像头加紧急制动。

越界后 agent 0.11 s 收到 PermissionError

projectcapsule.dev/tenant=acme 四层用同一个租户标签对齐：配额、网络策略、审计记录都能按这一个键聚合。这是这套组合最值钱的性质——身份贯穿始终，不需要另建映射表。

02

只需要接一根线

OpenShell 默认自己建命名空间。你已经有 Capsule 的租户体系，所以换成 operator 模式：平台建 ns 并打一个标签，OpenShell 按标签认领，租户流程一点不用动。

① 平台

Tenant 声明租户，顺带给它所有 ns 打标签 openshell.ai/workspace=true

→
② 租户

owner 自己建 ns，Capsule webhook 注入配额、LimitRange、默认网络策略

→
③ 网关

OpenShell 按标签发现 ns 并接管，日志确认 total=2

# capsule/tenants.yaml — 租户侧：打标签
spec:
  namespaceOptions:
    additionalMetadata:
      labels: {openshell.ai/workspace: "true"}
# openshell/values-plane-a.yaml — 控制面：认领
server:
  drivers:
    kubernetes:
      workspaceMode: operator
      operatorNamespaceLabel: "openshell.ai/workspace=true"

实测接管日志：operator namespace allowlist replaced from full relist total=2。之后 openshell sandbox create 就会在这个 ns 里落下 Sandbox CR + agent 容器 + supervisor 容器。

04

agent 到底做了什么

Tetragon 在内核层记录每一次尝试，事件自带租户、命名空间、容器和二进制名，不需要你另建映射表。

它连了谁

实测输出（compact 模式）

# 被拦掉了，但依然被记录
agent:egress-external  daddr=1.1.1.1:53
agent:egress-external  daddr=142.1.1.1:80
# 正常的集群内访问
agent:in-cluster       daddr=10.96.0.10:53
# agent 自己起了服务 = 暴露面变化
agent:listen           saddr=0.0.0.0:31339

它干了什么

POC 里真实命中的策略

  • 读配置 / 凭据 open-sensitive/etc/hosts
  • 删除文件 file-delete/tmp/x1
  • 起 shell risky-execpython3 → /bin/sh
  • 装包 package-manager/usr/local/bin/pip
  • 改运行身份 setuid-attemptuid 0（噪声高）

Tetragon 记的是"尝试"，策略决定"成不成功"。NetworkPolicy 和 OpenShell 只管放行与否，所以"agent 试过连哪儿"只有这一层看得到。再配上 OpenShell 的策略版本与判定（DENIED … engine:opa），才知道"连没连上"和"是谁放的"。

05

现在能用的，和还不能用的

下面这些不是设计意图，是这次实测的结论。绿勾都有命令输出，黄标都写清了缺什么、怎么补。

已验证

可以直接往前走

  • 端到端：一条命令建沙箱，agent 以 uid 10001 非 root 运行
  • 配额真拦：超限被拒，删除沙箱后用量回落
  • 网络边界：agent 连 apiserver / gateway 超时，只留 supervisor:5500
  • 预热池：0.25 s 到就绪
  • 观测：每条事件带租户 / 命名空间 / 二进制
  • 内核强制：指定解释器被拒（pip: Operation not permitted），python 不受影响
  • 策略下发：Capsule 自动把策略放进租户 ns（gtr READY=True）
  • 跨集群：平台集群抓租户集群三处指标，全部 up
  • 可移植：同一份 tenants.yaml 在第二个集群复现
还没搞定

上线前必须处理

  • 沙箱 DNS 没走 supervisor 沙箱解析走集群 CoreDNS，L7 出网策略的"代理 403"路径拿不到。→ 先在自己的环境复验这一段
  • runtimeClasses 白名单没拦住 Capsule 0.15 里 owner 用 kata 仍被接受，到 kubelet 才失败。→ 需要补一层 CEL / Kyverno 校验
  • 预热池的沙箱没有策略边界 池里领出来的沙箱不带 OpenShell supervisor 与凭据注入。→ 低延迟和"有策略"目前二选一
  • 没有 hypervisor 级隔离 kind 没有 gVisor 节点镜像；现有强度来自非 root + seccomp + NP + supervisor。→ 跑不可信代码前要上 gVisor / Kata
  • 单副本 + SQLite 网关默认部署只够 POC；多集群要每集群一套 gateway。→ 生产换 deployment + 外部 PostgreSQL
06

三步复现

前提：Docker 至少 8 GiB（两个 kind 集群常驻约 2.5–3 GiB）、已装 kind / kubectl / helm，内核有 BTF（Docker Desktop 6.12 满足）。

重建整个环境——两个集群加全部组件，约 10 分钟

bash poc/scripts/bootstrap.sh

给一个租户开通 sandbox——5 个动作全在脚本里，不用逐项配

bash poc/usage/01-onboard-tenant.sh acme

用起来——建沙箱、看日志、查当前策略

openshell workspace create --name acme
openshell --workspace acme sandbox create --name try1 \
  --cpu 200m --memory 256Mi -- python3 -u agent.py
openshell --workspace acme policy get try1   # 生效策略 + hash + 版本
